codeatlas

A Python CLI tool that automatically generates comprehensive, interactive HTML documentation for Python codebases using LLMs and Retrieval-Augmented Generation. It parses source code via AST analysis, builds a vector store for semantic retrieval, generates contextual documentation sections, produces validated Mermaid diagrams, and renders everything into a searchable HTML site.

Code Analysis

Layer 3

Statically analyzes Python source code using the built-in ast module. Extracts classes, functions, imports, call graphs, and cross-references without executing any code — making it safe to run on untrusted codebases.

▶ src/docgen/core/analyzer.py AST-based code analysis

CodeAnalyzer

def analyze_file(self, file_path: str) -> FileAnalysis

Parses a single Python file. Reads the file, runs ast.parse(), then walks the AST to extract entities and imports. Returns a FileAnalysis containing all structural data.

Entity Extraction (_extract_entities)

Walks top-level AST nodes to find:

  • Classes (ast.ClassDef) — name, docstring, methods list, source segment via ast.get_source_segment(), parent class from node.bases[0], line numbers
  • Functions (ast.FunctionDef) — name, docstring, source segment, line numbers

Import Extraction (_extract_imports)

Walks the full tree with ast.walk() to capture both forms:

  • import X → "X"
  • from X import Y → "X.Y"
def analyze_directory(self, directory: str, exclude_patterns: list[str] | None, max_files: int | None) -> list[FileAnalysis]

Recursively walks a directory with os.walk, filters by .py extension and glob-based exclude patterns (modifying dirs[:] in-place to prune subdirectories), and analyzes each file.

def analyze_function_calls(self, analyses: list[FileAnalysis]) -> dict[str, set[str]]

Builds a call graph using a custom FunctionCallVisitor(ast.NodeVisitor) that tracks the current function scope and records all ast.Call nodes — both direct calls (func()) and method calls (obj.method()).

def analyze_package_dependencies(self) -> dict[str, set[str]]

Combines requirements.txt parsing with import analysis to map module-to-module dependencies.

Design Choice: Pure static analysis via AST — no code execution, no dynamic imports. Safe for untrusted codebases with zero side effects.
produces → FileAnalysis produces → CodeEntity produces → call graph dict

LLM / RAG Layer

Layer 4

The semantic engine of the system. Embeds code chunks into a ChromaDB vector store, then uses an LCEL (LangChain Expression Language) chain to retrieve relevant context and generate documentation sections grounded in the actual code.

{context: [retrieved docs], question: original_prompt}

RetrieverConfig

ParameterTypeDefaultPurpose
kint10Number of documents to retrieve
search_type"similarity" | "mmr""similarity"Retrieval strategy
score_thresholdfloat | NoneNoneMinimum similarity score filter
fetch_kint20Documents to fetch before MMR reranking
lambda_multfloat0.5MMR diversity: 0 = max diversity, 1 = max relevance

Retrieval Strategies

  • Similarity Search (default) — Direct cosine similarity ranking. Fast and focused on relevance. Best for smaller codebases.
  • MMR (Maximal Marginal Relevance) — Two-phase: fetch top fetch_k by similarity, then rerank for diversity using lambda_mult. Avoids context dominated by a single module. Best for large codebases with repetitive patterns.
When to use MMR: Large codebases with repetitive patterns, when you want diverse examples rather than similar code, or when context is being dominated by a single module.

Layer 5

Protocol-based abstraction for LLM and embedding providers. Enables swapping between Anthropic Claude and OpenAI GPT without changing core logic. Uses lazy initialization and structured error classification.

class EmbeddingProvider(Protocol): model_name: str def embed_documents(self, texts: list[str]) -> list[list[float]] def embed_query(self, text: str) -> list[float]

Abstract Base Classes

Exception Hierarchy

Layer 12

All custom exceptions inherit from DocumentationError, enabling both granular per-layer error handling and broad catch-all recovery at the CLI level.

Exception ├── DocumentationError # base for all custom exceptions ├── CodeParseError # AST parsing failures ├── DiagramGenerationError # diagram generation failures │ └── DiagramValidationError # validation failures ├── ApiKeyError # missing or invalid API keys ├── VectorStoreError # ChromaDB operation failures ├── FileEncodingError # non-UTF-8 file encoding ├── TemplateError # Jinja2 rendering failures ├── LLMError # LLM invocation failures ├── EmbeddingError # embedding API failures ├── PathValidationError # path traversal / security └── CacheError # cache operation failures
Error handling strategy: The CLI entry point catches DocumentationError, ApiKeyError, CacheError, and ValueError at the top level with sys.exit(1). Each layer raises its appropriate exception type with contextual messages (file path, line number, etc.) enabling user-friendly error reporting.

Design Patterns

Reference

1. Protocol-Based Provider Abstraction

Narrow protocols (LLMProvider) for code with no LangChain dependency, extended protocols (LangChainLLMProvider) for code that needs LangChain objects. Keeps the dependency boundary clean while enabling provider swapping.

2. LCEL Chain Composition

Declarative chain: Retriever | Prompt | LLM | Parser. Enables streaming, async execution, and tool integration with simplified error handling through unified types.

3. Two-Level Caching

Vector Store Cache (persistent ChromaDB with metadata tracking) and Content Cache (section-specific with file dependency hashing). force_refresh bypasses all caches.

4. Configurable Validation Pipeline

Multiple modes (strict/permissive), per-rule disabling, and configurable severity thresholds. Follows the Rule pattern with a common ValidationRule protocol.

5. Template Loader Hierarchy

Custom → Default → Embedded fallback. Enables extensibility without breaking backward compatibility.

6. Lazy Provider Initialization

LLM and embedding objects created on first use, cached for subsequent calls. Reduces memory overhead and startup time.

7. Quality Mode Presets

FAST/BALANCED/BEST map to different Claude models, allowing users to control the cost/quality tradeoff with a single flag.

8. Error Classification Pattern

API errors classified into specific types (AUTH, RATE_LIMIT, QUOTA, etc.) via ERROR_PATTERNS, enabling intelligent retry strategies and user-friendly messages.

Design Decisions & Tradeoffs

Design

The reasoning behind the major architectural choices: vector store selection, chunking and retrieval strategy, chain composition, provider abstraction, caching granularity, validation, and parallelism.

1. Vector Store: ChromaDB

ChromaDB was chosen because it is embedded — it runs in-process with no server — persists to SQLite so the index survives restarts, integrates natively with LangChain via Chroma.from_documents(), supports both similarity and MMR search, and adds zero infrastructure cost for a CLI tool.

AlternativeWhy Not
FAISS Faster for large datasets, but no built-in persistence (serialization/deserialization would be manual) and no native MMR support.
Pinecone / Weaviate Managed services are overkill for a local CLI tool — they add a network dependency, latency, and cost.
Simple cosine similarity No chunking, no overlap, poor for long files. Retrieval would need to be reimplemented from scratch.
Scaling boundary: ChromaDB's SQLite backend is single-writer — fine for a single-user CLI tool, but it would bottleneck under concurrent writes. A hosted service processing many codebases concurrently would call for a managed vector DB like Pinecone for horizontal scaling and multi-tenancy.

2. Chunking Strategy

Each FileAnalysis generates two types of documents for embedding:

  • File content document — full source code with file path as metadata
  • Entity documents — one per class/function with formatted type, name, description, methods, and inheritance info

All documents are split with RecursiveCharacterTextSplitter(chunk_size=2000, overlap=200). The 200-char overlap ensures context isn't lost at chunk boundaries.

Character-based chunking handles the 80% case well — most functions and classes fit within 2000 chars. Semantic chunking (per-function) would be more precise but needs custom logic to handle nested classes, decorators, and multiline signatures. A future improvement would be AST-aware chunking that splits on class/function boundaries, so each retrieved chunk is a semantically complete unit; the AST is already available from the analysis layer.

3. Retrieval: Similarity vs. MMR

Similarity search is the default: direct cosine ranking is fast and works best for small-to-medium codebases, at the risk of context dominated by a single module. MMR is the alternative for large codebases with repetitive patterns: a two-phase process fetches 20 documents by similarity, then reranks down to 10 for diversity with lambda_mult=0.5 balancing relevance against diversity. It is slightly slower (2x retrieval, then filtering). Full parameter reference is in the LLM / RAG layer.

4. LCEL over Manual Composition

LCEL gives declarative chain composition (retriever | prompt | llm | parser) with built-in streaming support, async execution, and unified error handling. The alternative — manually calling the retriever, formatting a prompt string, sending to the LLM, and parsing the response — is more code, more error-prone, and harder to swap components. LCEL also makes the chain testable by mocking individual stages.

5. Two-Tier Provider Protocols

The narrow protocol (LLMProvider) keeps the dependency boundary clean: code that only needs to call an LLM (tests, simple scripts) doesn't need to import LangChain, while code that builds chains (the RAG pipeline) uses the extended protocol (LangChainLLMProvider). This also means a non-LangChain provider (e.g. calling the Anthropic API directly) could be added without breaking the core pipeline.

Lazy initialization: LLM and embedding objects are created on first use via get_langchain_llm() / get_langchain_embeddings(), then cached. This avoids creating expensive API clients at import time, reduces memory for unused providers, and makes testing faster since mocked providers skip real initialization.

6. Two-Level Cache Granularity

On-disk layout of the cache (see the Cache Layer for the per-section dependency table):

.docgen_cache/
└── df19a22d180ba003/          # SHA-256[:16] of source path
    ├── chromadb/
    │   ├── chroma.sqlite3          # vector embeddings (Level 1)
    │   └── [uuid]/                 # partition data
    ├── file_metadata.json          # per-file content hashes + mtimes
    └── section_cache.json          # generated section content (Level 2)

Why per-section dependency tracking instead of invalidating everything: LLM calls are the most expensive operation (~$0.03–$0.15 per section depending on model). If only a function's docstring changed, that affects "Key Classes" but not "Dependencies" or "Integration Points." The dependency system regenerates only what's actually stale — typically saving 60–80% of API costs on incremental runs.

Cache key: The project hash is SHA-256(absolute_source_path)[:16], so the same directory always maps to the same cache. Branch switching isn't handled explicitly — the file content hashes catch it: if files change after switching branches, those sections get regenerated. The git commit is tracked in metadata for debugging but isn't part of the cache key. A future improvement would be git-aware caching keyed by branch + commit.

7. Configurable Validation

LLM-generated Mermaid diagrams frequently have syntax errors: unescaped quotes in labels, reserved words as node IDs, missing direction declarations. Rather than shipping broken diagrams, the validation layer catches errors before output.

Strict mode is the default for production — errors fail validation. But during development, or when processing codebases with unusual naming (e.g. node IDs starting with digits), permissive mode lets non-critical issues pass as warnings. Individual rules can also be disabled by name. This avoids the "validation is too annoying so I'll just turn it off" problem.

8. Parallel Section Generation

# section_orchestrator.py
max_workers = min(len(section_names), MAX_PARALLEL_WORKERS)  # MAX = 5

with ThreadPoolExecutor(max_workers=max_workers) as executor:
    futures = {
        executor.submit(generate_section, name): name
        for name in section_names
    }
    for future in as_completed(futures):
        # each future independently succeeds or fails

ThreadPoolExecutor over asyncio: The work is I/O-bound (waiting for LLM API responses), so threads are appropriate. ThreadPoolExecutor is simpler than async — no need to refactor the entire codebase to be async or use async-compatible LangChain calls. With 5 workers and 5–8 sections, speedup is near-linear since each section is an independent API call. The GIL isn't a bottleneck because the time is spent waiting on network I/O, not CPU work.

Why cap at 5 workers: LLM API rate limits. Both Anthropic and OpenAI have per-minute request limits. Five concurrent requests is a safe default that provides good throughput without triggering rate limits; users on higher API tiers could increase this.

Zero-Cost Modes

  • --diagrams-only — $0.00. Generates Mermaid diagrams from pure static analysis. No API calls at all.
  • --dry-run — $0.00 for LLM, but may still embed if the vector store doesn't exist. Emits placeholder section content.

Latency Breakdown

Where time actually goes, for a medium-sized project (~200 files):

PhaseTime% of TotalBottleneck
AST analysis (200 files)~0.5s~1%CPU (ast.parse is fast)
Document chunking~0.2s<1%CPU (string splitting)
Embedding (cold, ~1000 chunks)~5-10s~15%Network (OpenAI API)
Embedding (cached)~0.1s<1%Disk (ChromaDB load)
Section generation (5 sections, parallel)~15-30s~70%Network (LLM API, longest section)
Diagram generation (5 types)~0.3s~1%CPU (template filling)
Diagram validation~0.05s<1%CPU (regex matching)
HTML rendering~0.1s<1%CPU (Jinja2)
Total (cold)~25-45s
Total (cached, few changes)~5-10s
The 70% insight: Section generation (LLM calls) dominates total latency. This is why parallel execution matters — 5 sections in parallel means wall-clock time is bound by the slowest section, not the sum. Without parallelism, a 5-section run would take ~60-150s instead of ~15-30s.

Further optimization has limited headroom: the hot path (LLM calls) is network-bound and already parallelized, and the caching layer eliminates it on incremental runs. The main remaining improvement would be LLM response streaming so partial results appear sooner in the HTML output — that improves perceived latency but doesn't reduce total time.

Failure Modes & Recovery

Operations

How the system behaves when things go wrong: partial-success design for section generation, a taxonomy of failure scenarios, and known gaps in recovery.

Partial Failure: Section Generation

The system is designed for partial success. Each section is generated independently (separate futures in ThreadPoolExecutor). If one section fails:

  • The error is caught and the section is replaced with "*Error generating this section: {error}*"
  • Other sections continue generating normally
  • The error list is returned to the caller alongside successful sections
  • HTML output is generated with whatever succeeded

Failure Taxonomy

FailureImpactRecovery
LLM returns garbage/hallucinated content Section content is wrong but syntactically valid No automatic detection. This is a known limitation. The RAG chain grounds output in retrieved code, which reduces hallucination, but doesn't eliminate it. Future: add an LLM-as-judge validation pass.
LLM rate limit (429) Section generation fails Error classified as RATE_LIMIT. Currently fails the section. Future: exponential backoff retry.
Invalid API key All LLM calls fail Detected early in provider initialization. Raises ApiKeyError, CLI exits with a clear message.
Syntax error in source file One file skipped ast.parse() failure caught per-file. Warning logged, other files continue.
Diagram validation failure Diagram not included in output In strict mode, failed diagrams are omitted. In permissive mode, warnings are logged but the diagram is included.
Cache corruption Stale or broken content --force-refresh rebuilds from scratch. --clear-cache deletes the cache entirely.
Stale cache (subtle) Section doesn't reflect recent changes Hash-based invalidation catches file-level changes. But if the LLM prompt changes (code update), cached sections won't regenerate. Future: include the prompt hash in the cache key.
Known limitation: There is no retry logic for transient API failures. The error classification infrastructure exists (the ErrorType enum) but retries aren't implemented — the system fails fast instead of retrying. For a CLI tool this is acceptable since the user can re-run; for a hosted service, retry with backoff would be essential.

What Breaks at 10K Files

  • Memory — All FileAnalysis objects are held in memory simultaneously. With full source content per file, a 10K-file codebase could need 1–2 GB. Mitigation: stream-process files, keep only metadata in memory, write content to disk.
  • Vector store size — ChromaDB with 10K files × ~5 chunks each = 50K vectors. ChromaDB handles this, but initial indexing takes minutes. Mitigation: incremental indexing via VectorStoreCache already handles this — only changed files are reindexed.
  • Context window saturation — Retrieving 10 chunks of 2000 chars = ~20K chars of context. With the prompt template overhead, this approaches Claude's useful context. Mitigation: reduce retriever_k or switch to MMR for diverse but smaller context.
  • Cost — More files means more embedding calls. At $0.02/M tokens for text-embedding-3-small, 50K chunks is still under $0.10, so cost scales linearly but stays cheap for embeddings. LLM costs are per-section, not per-file.

The max_files Safety Valve

The analyze_directory(..., max_files=N) parameter stops analysis after N files. This prevents accidental processing of huge monorepos and keeps memory bounded. Combined with --exclude patterns, users can target the relevant subset of a large codebase.

Path to a Hosted Multi-Tenant Service

Scaling to a hosted multi-tenant service would require three changes: (1) replace ChromaDB with a managed vector DB (e.g. Pinecone) for multi-tenancy and horizontal read scaling; (2) move section generation to a task queue (Celery/SQS) with per-tenant rate limiting; (3) add a caching layer (Redis) in front of the vector store for hot codebases. The pipeline architecture stays the same — these are infrastructure swaps, not redesigns.
